Paso 1

Decide antes de programar

Si no puedes describirlo en 200 palabras, no puedes entregarlo en 10 horas

Paso 1 / Decide

No abras el editor primero

  • ▸Primer movimiento del hackathon: una ventana de chat, no npm create
  • ▸Usa ChatGPT / Gemini / Claude para redactar tu PRD
  • ▸PRD = alcance + no-alcance + criterios de éxito. Acota el alcance.
  • ▸Si no puedes describirlo en 200 palabras, no puedes entregarlo en 10 horas
Ejemplo · DeliverFirst

El prompt → el PRD

Prompt
I'm building a hackathon project: an app that
helps small-business delivery operators decide
the ORDER of their stops for the day.

Audience: couriers, mobile car detailers,
traveling fruit/vegetable sellers — anyone with
5–20 stops in a day.

Key insight: navigation already exists (Maps
does that). The hard part is SEQUENCING — which
client gets visited first?

Write me a 1-page PRD: problem, personas, MVP,
non-features, demo success criteria.
Resultado (recortado)
# DeliverFirst

Problem  Small-business delivery operators lose
         hours deciding which stop to do next.
         Maps tells them how to get there; nothing
         tells them which to do first.

Personas Courier · mobile car detailer ·
         traveling produce seller

MVP      1. Add stops (address, priority, window)
         2. Smart-order the stops
         3. Mark done / drag-reorder
         4. Day-end summary

Not MVP  Turn-by-turn nav · multi-day ·
         multi-courier · payments

Demo     10 stops in <2 min · AI order beats
         naive · one persona walks the morning

Elige tu herramienta de diseño

  • ▸UI generativa: Google Stitch (gratis), Claude Design, ChatGPT, Gemini, Lovable, v0

Paso 3

Divide el trabajo

Maximiza el paralelismo. Minimiza la espera.

Paso 3 / División

Roles, escritos por el LLM

  • ▸Pega el PRD y el diseño de vuelta, pide roles para un equipo de N
  • ▸Optimiza para paralelismo — slices full-stack, no capas
  • ▸Objetivo: nadie espera a nadie
Ejemplo · DeliverFirst

División para un equipo de 3

Prompt
Here's the PRD [paste above]. Team of 3 at
the hackathon.

Split into roles that:
- Maximize parallel work (full-stack slices,
  not layers)
- Have minimal handoffs
- Each ship something visible early
Resultado (recortado)
Role 1 — Stop entry & list
  Form + list screen
  Owns: <Form/>, <StopList/>, /api/stops

Role 2 — Smart ordering engine
  LLM prompt + ranking
  Owns: /api/order, lib/order/, eval harness

Role 3 — Day flow + demo polish
  Today's plan + done flow + Vercel deploy
  Owns: /today, /summary, /demo, vercel.json

Paso 4 / Código

Elige tu herramienta de código

  • ▸Difieren menos de lo que crees
  • ▸Elige lo que tus dedos ya conocen
La regla principal

Planificación > Ejecución

Dedica tiempo al plan. La ejecución es la parte fácil.

Planificación

Cómo planificar bien

  • ▸LLMs inteligentes para planificar, LLMs rápidos para ejecutar
  • ▸Haz que el agente produzca un plan escrito antes de cualquier código
  • ▸No te saltes el plan para "ahorrar tiempo" — te cuesta 3× después
Ejecución

Genera el scaffold en un one-shot

  • ▸Alimenta al agente con PRD + diseño + roles → pídele la app inicial completa en un one-shot
  • ▸No apuntas a producción. Apuntas a código corriendo en 20 minutos.
  • ▸Desde aquí, cada miembro del equipo empieza a iterar desde el mismo scaffold
Entrega en equipo

Commit rápido

  • ▸Commits pequeños, frecuentes, con nombre
  • ▸Push cada ~15 minutos en las primeras horas
  • ▸Los conflictos matan equipos — los commits pequeños mantienen la ventana de merge angosta
Entrega en equipo

Worktrees — un repo, N checkouts en paralelo

# Claude Code — flag de worktree integrado
$ claude --worktree role-1

# Otras herramientas — git worktree + lanzar manualmente
$ git worktree add ../role-2   role-2
$ cd ../role-2 && codex          # Codex

$ git worktree add ../role-3   role-3
$ cd ../role-3 && cursor .       # Cursor


DeliverFirst/                  ← main
  ├── ../role-1                ← Rol 1 + Claude Code
  ├── ../role-2                ← Rol 2 + Codex
  └── ../role-3                ← Rol 3 + Cursor
Entrega en equipo

Permisos — modo auto

  • ▸Configura el agente en modo auto (el más seguro): trabaja automáticamente, pero pausa pidiendo tu aprobación en cada cambio
  • ▸Tú eres el freno; el agente es el motor
  • ▸Atrapa los refactors malos y los comandos sorpresa antes de que toquen tu árbol
  • ▸Más lento que full-auto, pero la pérdida es pequeña cuando el plan fue bueno
Entrega en equipo

Sandboxes en la nube — cuando estés listo para soltar

  • ▸Corre agentes en contenedores en la nube (gestionados por Claude / Cursor / Codex)
  • ▸Radio de impacto acotado — deja que los agentes vayan en full-auto sin mirarlos
  • ▸Especialmente útil para las horas "mientras duermo"
Entrega en equipo

Skills — solo cuando los necesitas

  • ▸No desarrolles un Skill a menos que sea estrictamente necesario
  • ▸Para prompts de una sola vez, solo promptea — los skills son overhead
  • ▸Ejemplo: una tarea repetida Y enredada — acceso a DB local, configs, scripts de deploy
https://www.skills.sh/
Paso 5

Mantén el stack simple

Si no se nota en la demo, no lo construyas

Paso 5 / Stack

El stack para hackathon

  • ▸Frontend: Next.js + Tailwind, deploy en Vercel
  • ▸Agentes: ADK + GCP Agent CLI
  • ▸Almacenamiento: Supabase (DB) + Astra como VectorDB para búsqueda semántica
  • ▸Regla: si no se nota en la demo, no lo construyas
