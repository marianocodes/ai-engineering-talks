Standard #1

init

Bootstrap your repo. Run once. The agent reads your code and writes a CLAUDE.md tuned to it.

$ claude
> /init

# Analyzes the repo, then writes CLAUDE.md with:
#   • project structure
#   • build & test commands
#   • conventions worth remembering
#   • known pitfalls
Standard #2

AGENTS.md / CLAUDE.md

The agent's "always-on" context. Lives at the repo root. Edit it like code.

# Project: Telescoped

## Commands
- Install: bun install
- Test:    bun test
- Build:   bun run build

## Conventions
- Use Bun, not Node
- Prefer composition over inheritance
- No console.log in committed code
Standard #3

Skills

Reusable instructions the agent loads on demand. One per task type. Progressive disclosure.

---
name: slides
description: Generate an HTML slide deck for an
  AI Engineering talk from a user-provided outline.
---

# Procedure
1. Read template.html
2. Compose slides from snippets
3. Write slides.html
Standard #4

Hooks

Shell commands that run around tool calls. Lint after edits. Notify on completion. Enforce policy.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "bun lint" }
        ]
      }
    ]
  }
}
Standard #5

Execution modes

Plan mode
  • ▸Read-only — no edits
  • ▸Forces alignment before code
  • ▸Use for big or ambiguous changes
Code mode
  • ▸Free to edit, run, ship
  • ▸Use once the approach is clear
  • ▸The default for known territory
Standard #6

Permissions — the safety dial

  • ▸Ask each time — maximum control, slowest
  • ▸Accept edits — auto-approve file changes, gate everything else
  • ▸Auto / bypass — full speed, with caveats
  • ▸The dial moves with trust and blast radius
Advanced patterns

Subagents

  • ▸Own context window — clean slate, no pollution from parent
  • ▸Only talk to parent — they can't message each other
  • ▸Best for repetitive sub-tasks inside one job
  • ▸Keep the main agent focused on the task, not the searches
Advanced patterns

Team agents

  • ▸Multiple agents sharing the same workspace
  • ▸Each has a role — researcher, implementer, reviewer
  • ▸Best for multi-stage work where roles matter
  • ▸You set the goal — a lead agent coordinates
Parallel work

git worktrees — N agents, one repo

  • ▸One clone, many checkouts — each its own folder
  • ▸Each worktree gets its own agent
  • ▸No branch-switching, no stashing, no stepping on each other
  • ▸Three agents shipping in parallel is realistic now
Parallel work

Worktrees in practice

$ git worktree add ../feat-auth        feat-auth
$ git worktree add ../feat-billing     feat-billing
$ git worktree add ../feat-onboarding  feat-onboarding


app/                            ← main worktree
  ├── ../feat-auth              ← agent #1
  ├── ../feat-billing           ← agent #2
  └── ../feat-onboarding        ← agent #3

The problem

Local has a ceiling

  • ▸Even with auto-accept, you're still babysitting
  • ▸Permission fatigue → people start blindly approving
  • ▸One bad command can wreck a working tree
  • ▸The risk is small, but it scales with how much you delegate

  • ▸No permission fatigue — supervise outcomes, not commands
  • ▸Bounded blast radius — failures stay inside the box
