Step 1

Decide before you code

If you can't describe it in 200 words, you can't ship it in 10 hours

Step 1 / Decide

Don't open the editor first

  • ▸First move of the hackathon: a chat window, not npm create
  • ▸Use ChatGPT / Gemini / Claude to draft your PRD
  • ▸PRD = scope + non-scope + success criteria. Bound the weekend.
  • ▸If you can't describe it in 200 words, you can't ship it in 10 hours
Worked example · DeliverFirst

The prompt → the PRD

Prompt
I'm building a hackathon project: an app that
helps small-business delivery operators decide
the ORDER of their stops for the day.

Audience: couriers, mobile car detailers,
traveling fruit/vegetable sellers — anyone with
5–20 stops in a day.

Key insight: navigation already exists (Maps
does that). The hard part is SEQUENCING — which
client gets visited first?

Write me a 1-page PRD: problem, personas, MVP,
non-features, demo success criteria.
Result (trimmed)
# DeliverFirst

Problem  Small-business delivery operators lose
         hours deciding which stop to do next.
         Maps tells them how to get there; nothing
         tells them which to do first.

Personas Courier · mobile car detailer ·
         traveling produce seller

MVP      1. Add stops (address, priority, window)
         2. Smart-order the stops
         3. Mark done / drag-reorder
         4. Day-end summary

Not MVP  Turn-by-turn nav · multi-day ·
         multi-courier · payments

Demo     10 stops in <2 min · AI order beats
         naive · one persona walks the morning

Step 3

Split the work

Maximize parallel. Minimize waiting.

Step 3 / Split

Roles, written by the LLM

  • ▸Paste the PRD and the design back, ask for roles for a team of N
  • ▸Optimize for parallelism — full-stack slices, not layers
  • ▸Goal: nobody waits on anyone
Worked example · DeliverFirst

Split for a team of 3

Prompt
Here's the PRD [paste above]. Team of 3 at
the hackathon.

Split into roles that:
- Maximize parallel work (full-stack slices,
  not layers)
- Have minimal handoffs
- Each ship something visible early
Result (trimmed)
Role 1 — Stop entry & list
  Form + list screen
  Owns: <Form/>, <StopList/>, /api/stops

Role 2 — Smart ordering engine
  LLM prompt + ranking
  Owns: /api/order, lib/order/, eval harness

Role 3 — Day flow + demo polish
  Today's plan + done flow + Vercel deploy
  Owns: /today, /summary, /demo, vercel.json
Step 4

Code with AI

Where most of the craft lives

Step 4 / Code

Pick your coding tool

  • ▸Claude Code · Codex · Cursor · Antigravity · Gemini CLI
  • ▸They differ less than you think
  • ▸Pick what your fingers already know
The big rule

Planning > Execution

Take time on the plan. The execution is the easy part.

Planning

How to plan well

  • ▸Smart LLMs for planning, fast LLMs for execution
  • ▸Make the agent produce a written plan before any code
  • ▸Don't skip the plan to "save time" — it costs you 3× later
Execution

One-shot the scaffold

  • ▸Feed the agent PRD + design + roles → ask for the whole initial app in one shot
  • ▸Not aiming for production. Aiming for running code in 20 minutes.
  • ▸From here, every teammate starts iterating from the same scaffold
Team shipping

Commit fast

  • ▸Small, frequent, named commits
  • ▸Push every ~15 minutes in the early hours
  • ▸Conflicts kill teams — small commits keep the merge window tight
Team shipping

Worktrees — one repo, N parallel checkouts

# Claude Code — built-in worktree flag
$ claude --worktree role-1

# Other tools — git worktree + launch manually
$ git worktree add ../role-2   role-2
$ cd ../role-2 && codex          # Codex

$ git worktree add ../role-3   role-3
$ cd ../role-3 && cursor .       # Cursor


DeliverFirst/                  ← main
  ├── ../role-1                ← Role 1 + Claude Code
  ├── ../role-2                ← Role 2 + Codex
  └── ../role-3                ← Role 3 + Cursor
Team shipping

Permissions — auto-mode

  • ▸Set the agent to auto-mode (safest): it works automatically, but pauses for your approval on every change
  • ▸You're the brake; the agent is the engine
  • ▸Catches the bad refactors and surprise commands before they hit your tree
  • ▸Slower than full-auto, but the loss is small when your plan was good
Team shipping

Cloud sandboxes — when you're ready to let go

  • ▸Run agents in cloud containers (Claude / Cursor / Codex managed)
  • ▸Blast radius bounded — let agents go full-auto without watching
  • ▸Especially useful for the "while I sleep" hours
Team shipping

Skills — only when you need them

  • ▸Don't develop a Skill unless strictly necessary
  • ▸For one-off prompts, just prompt — skills are overhead
  • ▸Example: a task that's repeated AND fiddly — local DB access, configs, deploy scripts
https://www.skills.sh/
